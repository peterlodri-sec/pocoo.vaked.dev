Perf tips and Metal learnings from Qwave

A browser on Apple Silicon has two kinds of performance: the kind you write, and the kind the OS already does for you. This page collects the measurement discipline, the allocation tricks, and the GPU facts that survived contact with a real codebase — Qwave, a WebKit-native macOS browser with CI-asserted malloc gates.

Qwave perf sessions · 2026-08-13 → 14 · all numbers measured, most of them CI-pinned

01The discipline: measure before you believe

Every optimization below was either rejected or accepted by a number, not by intuition. The rules that made that possible:

  • Allocation count is the contract. `mallocCountTotal` is near-deterministic for a given code path, survives noisy machines, and is CI-checked with a 25% p90 tolerance. Wall-clock is never gated — it is collected for trends only. ARC traffic (retain/release counts) gets a 5% gate.
  • A benchmark run on an unquiesced machine is rejected, not recorded. Thermal state must be nominal, no background builds, load average below 2.0. One sample is not a measurement; report median, p90, and spread.
  • Thresholds are reviewed like code. A jump in allocations is a diff someone must own.

The FTS5 lesson. "The full-table scan on the keystroke path — surely SQLite's FTS5 index fixes it." Implemented end-to-end (migration, external-content index, sync triggers, upgrade backfill, LIKE fallback for short queries). It was faster on wall-clock — and 4.4× worse on the gated metric: 2,143 mallocs/query vs 486 for LIKE at 50k rows, failing the 1,298 threshold by 2.1×. The "obvious" optimization lost on the contract the team actually commits to. The deferral was right; now it has numbers.

02Allocation tips that shipped

Single-pass escaping beats chained replacingOccurrences

Four chained `replacingOccurrences` calls allocate a full string per pass. A single scan into one reserved buffer with the same four-case mapping is behavior-identical:

var result = ""
result.reserveCapacity(string.count + string.count / 8)
var i = string.startIndex
while i < string.endIndex {
    switch string[i] {
    case "&": result.append("&amp;")
    case "<": result.append("&lt;")
    case ">": result.append("&gt;")
    case "\"": result.append("&quot;")
    default: result.append(string[i])
    }
    i = string.index(after: i)
}
return result

The same file had a per-character `escape(String(string[i]))` — a heap String per character, each escaping through four replacingOccurrences. That was ~6 allocations per plain-text byte. One pass fixed it. MarkdownCompiler: 8,983 → 1,069 mallocs per internal doc page.

Cache the regexes

Eight `NSRegularExpression` patterns were being compiled on every pass of the inline formatter — dozens of compilations per paragraph. Compiled once per process in a `@unchecked Sendable` box, because `NSRegularExpression` predates Sendable but is documented thread-safe.

Keep Substrings, not Strings

`source.split(...).map(String.init)` materializes every line as a heap String. Keep the slices; only allocate the blocks you actually return.

Bounded top-N instead of full sort

The omnibox ranked 500 history suggestions per keystroke by full-sorting then prefixing. Keep a bounded top-6 heap and discard the rest: the same result, none of the tail. Combined with Substring host/URL drops and a `Set` dedup with reserved capacity: 4,370 → 1,011 mallocs per keystroke.

Cache the prepared statements

`sqlite3_prepare_v2` on every call is a parse + compile of the SQL. Cache by SQL text; the hot queries stop re-preparing. (And add the indexes the query plan actually needs — composite over the WHERE/ORDER columns, not just the obvious ones.)

Byte-identical contracts need diff harnesses

Rewriting a compiler? The output is the contract. Old and new implementations compiled side-by-side, run over edge cases (nested parks, escaped quotes, CRLF input), outputs diffed byte-for-byte. This caught a real regression — a "cleaner" single-pass marker resolution that broke nested parks (a math block wrapping a code fence). The proven loop went back in; the escape and regex wins stayed.

03Energy: polling is a battery bug

The energy governor sampled thermal state, Low Power Mode, and window occlusion once per 30-second tick (10s leeway). Flip Low Power Mode and the policy — 3× shorter hibernation timeout, background media suspended, warm processes dropped — applied up to 40 seconds later.

The OS broadcasts all three events. Three `NotificationCenter` observers run the existing tick immediately, throttled to one per 5s so occlusion storms coalesce; the 30s timer stays the steady cadence and is never throttled. Reaction: milliseconds instead of 40 seconds. Zero policy logic changed — only when it runs.

Two details worth stealing: guard the async bootstrap (observers installed in `didFinishLaunching` can fire before the app's own launch Task finishes), and expect SDK renames — the power notification is `NSNotification.Name.NSProcessInfoPowerStateDidChange`, not the obvious `ProcessInfo.powerStateDidChangeNotification`. The typecheck caught it before CI would have.

04Metal learnings: know who owns the pixels

The most asked question about a Mac app is "why aren't you using Metal?" For a WebKit browser the honest answer is: you already are.

  • The wave background on Qwave's start page is a WebGL fragment shader. It compiles and runs in WebKit's GPU process, which on Apple Silicon is Metal underneath. An app-side `MTKView` port would not move it from CPU to GPU — it would double-composite it across a process boundary. Strictly worse.
  • So the lever isn't the API, it's demand control: the shader ran unthrottled at up to 120 full-window frames per second on ProMotion, per tab, per WebContent process. Cap at 30fps — imperceptible for slow FBM drift, halves GPU work at 60Hz, quarters it at 120Hz — and cancel the render loop on `visibilitychange` so occluded windows burn nothing.
  • Energy is the metric, not framerate. A background wave at 120fps nobody is looking at isn't "smooth", it's heat. `prefers-reduced-motion` is both an accessibility feature and a power budget.

    • We then measured the wave to prove the demand-control claim. The exact shipped shader — 5-octave fbm, domain warp, 100 sin per pixel — ported to a Metal compute kernel and a scalar Swift reference, timed at the real 1512×982 canvas:

    • GPU (Metal compute, M1 Pro): 1.85 ms/frame (kernel ~1.6 ms; 1.8–2.5 across runs) — ~550 fps potential
    • CPU (scalar Swift, 1 core): 757.72 ms/frame — 1.32 fps; 742M sin calls verified executing
    • ~409× speedup. The wave is not optional CPU work; WebKit already runs it on the GPU in its own process. An app-side port would double-composite, not accelerate.
    • The 30fps cap uses 5.6% of the frame budget at this resolution — the cap is nearly free in GPU time; its real saving is energy per frame across N tabs.
  • The warm-process trick was a myth on this platform: `WKProcessPool` has been a no-op since macOS 12 ("creating and using multiple instances no longer has any effect"), yet the energy policy still carried the knob, with a comment claiming a 45MB/100–200ms tradeoff the API cannot deliver. Removed; the deprecation warnings left with it.

We audited the remaining app-side drawing before reaching for Metal: the MemoryWave panel is plain SwiftUI text, the favicon loader is decode-and-cache, tab snapshots are WebKit's. The first Metal port would have been speculative — the codebase's own drawing is thin because WebKit owns the pixels, and that is correct.

06Concurrency: the new primitives, measured

The headline is the negative result: the new synchronization.Mutex is not faster than the classics — and that is fine. Its value is ergonomics and safety, not speed. Under 8-thread contention (2M increments each), the lock-free Atomic<Int> wins; every lock-based primitive ties:

07The +0 ABI trap (and the ~Copyable non-result)

My first ARC benchmark measured nothing. A 50M-iteration loop calling an @inline(never) function that only reads its parameter took 17 ms — because Swift's ABI passes read-only parameters at +0 (borrowed). No retain, no release, ever. The copyable vs ~Copyable comparison only exists once the callee stores the value; that is the sentence to keep: measure ARC by making the value escape, not by calling a function that looks at it.

With the escape forced (callee stores to a global), the fair comparison — fresh construction on both sides, 50M calls — lands at parity: copyable 377.6 ms vs ~Copyable consume 377.7 ms. Refcount churn on a 40-byte struct with one class reference is ~free (7.5 ns/call including construction). ~Copyable buys exclusivity semantics and large buffers, not ARC wins on small values. Same machine, same build, two samples; the reuse-vs-construct trap that briefly "proved" copyable faster is in the repo's hacking log.
