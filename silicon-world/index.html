Perf tips and Metal learnings from Qwave

A browser on Apple Silicon has two kinds of performance: the kind you write, and the kind the OS already does for you. This page collects the measurement discipline, the allocation tricks, the SQLite unified memory tuning, and the GPU facts that survived contact with a real codebase — Qwave, a WebKit-native macOS browser with CI-asserted malloc gates.

Qwave perf sessions · 2026-08-13 → 15 · all numbers measured, most of them CI-pinned

01The discipline: measure before you believe

Every optimization below was either rejected or accepted by a number, not by intuition. The rules that made that possible:

  • Allocation count is the contract. mallocCountTotal is near-deterministic for a given code path, survives noisy machines, and is CI-checked with a 25% p90 tolerance. Wall-clock is never gated — it is collected for trends only. ARC traffic (retain/release counts) gets a 5% gate.
  • Check that the gate runs. Added 2026-08-16, the hard way — see below. A threshold file committed next to a CI job is not a gate. It is a gate if you have watched it fail.
  • Benchmarking dead code manufactures a number. zig-core's packet filter looked like an obvious candidate for an arena allocator. It allocates nothing per packet — and more to the point, Swift never calls it; the data plane is WireGuardKit's. So the stats it reports are structurally always zero, which reads as "nothing was filtered" rather than "nothing is filtering". Adding a benchmark would have produced a clean, meaningless graph.
  • A benchmark run on an unquiesced machine is rejected, not recorded. Thermal state must be nominal, no background builds, load average below 2.0. One sample is not a measurement; report median, p90, and spread.
  • Thresholds are reviewed like code. A jump in allocations is a diff someone must own.

The gate that was never running. Everything above assumed the thresholds were enforced. Seven of the eight were not. swift package benchmark thresholds update writes threshold filenames through a space → underscore filter; the reader looks them up under the benchmark's raw name. Any benchmark whose name contains a space therefore writes a file it can never find again — and is dropped from the check silently, with a zero exit. Only OmniboxParser.parse, the one name without a space, was ever actually gated.

Fixed by renaming the benchmarks to the spelling the writer already uses, so filenames stay put (commit 30530c9). Proved by mutation rather than assertion: 11000 → exit 0 EQUAL, 5000 → exit 1 WORSE, 11000 → exit 0 EQUAL. The moment it came back to life it found HistoryStore.entries sitting 58% below its recorded baseline — 1,298 → 537 — because nothing had compared them in months.

Two smaller traps in the same tooling, both of which produce confident numbers that mean nothing: malloc counting is inert without jemalloc on PKG_CONFIG_PATH (it reports zeroes, not an error), and the figure the runner displays is per-call while the threshold file stores the raw per-1000 total. Calibrate against a known benchmark before trusting either.

The FTS5 lesson. "The full-table scan on the keystroke path — surely SQLite's FTS5 index fixes it." Implemented end-to-end (migration, external-content index, sync triggers, upgrade backfill, LIKE fallback for short queries). It was faster on wall-clock — and 4.4× worse on the gated metric: 2,143 mallocs/query vs 486 for LIKE at 50k rows, failing the 1,298 threshold by 2.1× (commit 3ca52f1). The "obvious" optimization lost on the contract the team actually commits to. The deferral was right; now it has numbers.

02Allocation tips that shipped

Single-pass escaping beats chained replacingOccurrences

Four chained replacingOccurrences calls allocate a full string per pass. A single scan into one reserved buffer with the same four-case mapping is behavior-identical (MarkdownCompiler.swift, commit 8d1e342):

var result = ""
result.reserveCapacity(string.count + string.count / 8)
var i = string.startIndex
while i < string.endIndex {
    switch string[i] {
    case "&": result.append("&amp;")
    case "<": result.append("&lt;")
    case ">": result.append("&gt;")
    case "\"": result.append("&quot;")
    default: result.append(string[i])
    }
    i = string.index(after: i)
}
return result

The same file had a per-character escape(String(string[i])) — a heap String per character, each escaping through four replacingOccurrences. That was ~6 allocations per plain-text byte. One pass fixed it. MarkdownCompiler: 8,983 → 1,069 mallocs per internal doc page.

Cache the regexes in Sendable boxes

Eight NSRegularExpression patterns were being compiled on every pass of the inline formatter — dozens of compilations per paragraph. Compiled once per process in an @unchecked Sendable box, because NSRegularExpression predates Sendable but is documented thread-safe.

Keep Substrings, not Strings

source.split(...).map(String.init) materializes every line as a heap String. Keep the slices; only allocate the blocks you actually return.

Bounded top-N instead of full sort

The omnibox ranked 500 history suggestions per keystroke by full-sorting then prefixing. Keep a bounded top-6 heap and discard the rest: the same result, none of the tail (OmniboxSuggester.swift). Combined with Substring host/URL drops and a Set dedup with reserved capacity: 4,370 → 1,011 mallocs per keystroke.

// Bounded linear scan keeping only top-k suggestions
var topEntries: [(score: Double, entry: HistoryEntry)] = []
topEntries.reserveCapacity(limit + 1)
for entry in history {
    guard let s = matchScore(q, entry: entry) else { continue }
    if topEntries.count < limit || s > (topEntries.last?.score ?? -.infinity) {
        let idx = topEntries.firstIndex { s > $0.score } ?? topEntries.count
        topEntries.insert((score: s, entry: entry), at: idx)
        if topEntries.count > limit { topEntries.removeLast() }
    }
}

A regex pass costs ~4 allocations even when it matches nothing

The obvious targets were already fixed — the regexes were cached, the lines were Substrings, the buffers were reserved. The compiler still burned 33 allocations emitting a six-character table cell. The reason: inline() ran all eight patterns unconditionally, and an NSRegularExpression pass with zero matches still costs about four — NSString bridge, output buffer, tail substring, bridge back. At ~18 inline calls per page that was ~700 of 1,069.

The fix is to not run the pass. Gate each one on a UTF-8 scan for a byte the pattern cannot match without — \*\*([^*]+)\*\* cannot fire without a *. These are necessary conditions, not heuristics, which is why output stays byte-identical. MarkdownCompiler: 1,069 → 340 mallocs per internal doc page (commit ed62e74), verified by running a 50-case corpus through the old and new compilers side by side and diffing bytes.

Measured on the way past, and worth knowing on its own: ns.substring(with:) costs 2 allocations; String(text[Range(r, in: text)!]) costs 0, because the result fits Swift's small-string form.

The allocation was the lowercasing, not the URL access

The remaining 1,011 mallocs per keystroke looked like URL work — absoluteString and url.host on every candidate. Both are effectively free: Foundation hands back stored storage, and a host like site42.example fits Swift's 15-byte small-string limit, so it never touches the heap. The whole cost was two lowercased() calls per entry, 500 entries deep.

So stop producing the strings. Match byte-wise over the UTF-8 storage that already exists — but only for pure-ASCII, CR-free inputs, with everything else falling through to the original scoring, kept verbatim. That boundary is load-bearing, not defensive: İ lowercases to two scalars, U+212A KELVIN SIGN lowercases to ASCII k, and CR LF is ASCII's one multi-scalar grapheme. OmniboxSuggester: 1,011 → 11 mallocs per keystroke (commit 30530c9).

The index that would have been a lie. The plan was a prepared index: lowercase every candidate once, reuse it across keystrokes. Measurement killed it. In production the candidate list is a query-dependent SQL result — history.entries(matching: query, limit: 50), rebuilt per keystroke — so there is nothing stable to index. Worse, the benchmarked entry point has no caller in the app at all. An index could only have looked like a win by hoisting construction out of the measured loop, which the real code path does not do. It would have produced a beautiful number and changed nothing for the user. The smaller, honest fix reached 11 anyway — and since no cache exists, the staleness bug it would have introduced cannot exist either.

Serialization, not data structures

The rule-list compiler was the last big site: 49,552 allocations to compile 1,000 filter rules, ~49.5 per rule. The obvious culprit was [[String: Any]] — a Dictionary per rule, every value a boxed existential, every key a heap String. Phase attribution said otherwise:

substring split                11      —
components(separatedBy:)    1,012    2.0%
+ per-line trim             2,012    2.0%
+ parse                     7,262   10.6%
+ regex construction       ~21,000  27.7%
+ [String: Any] dicts      ~27,000  12.1%
+ JSONSerialization        49,552   45.5%   <- the actual answer

The dictionaries were third. Nearly half the cost was JSONSerialization turning those structures back into text. Writing UTF-8 bytes into one reserved buffer, with regex escaping and JSON escaping fused into a single pass, lands within 6 allocations of the parse-only probe — everything outside the parser is now free. 49,552 → 7,268 (commit 763bc1f).

Found in passing, and worth its own sentence: escapeHost was calling .replacingOccurrences(of: "\\.", with: "\\.") — identical needle and replacement — paying a full NSString bridge per rule to produce the string it already had.

Three hypotheses, three misses. Every one of these three optimizations was preceded by a confident, specific, wrong guess about where the allocations were.

Markdown: predicted per-line splitting, missing reserveCapacity, uncached regexes. All three had already been fixed in an earlier pass. The real cost was regex passes that matched nothing.
Omnibox: predicted absoluteString and url.host. Both are free — Foundation returns stored storage, short hosts fit the small-string form. It was lowercased(), entirely.
Rule compiler: predicted the boxed dictionaries. They came third, at 12%. It was serialization, at 46%.

The pattern is not that the guesses were careless — each named a real, plausible, textbook allocation source. It is that the textbook sources had mostly been fixed already, so what remained was, by definition, the thing nobody thinks of. Past a first cleanup pass, intuition is measuring your own reading habits rather than the program. Attribute by phase before touching anything; the profile is cheap and the guess is worth nothing.

Declarative Net Request (MV3 DNR): Native WebKit JSON Compilation

Rather than running JavaScript extension background scripts to inspect and block network requests, Qwave compiles MV3 declarativeNetRequest rulesets directly into native WebKit WKContentRuleList JSON format (DeclarativeNetRequest.swift, PR #48 / commit 325fb0c). The rules execute inside WebKit's native C++ engine with 0 ms JavaScript bridge overhead.

02bNew Swift, and the two walls it runs into

The allocation work above ends where the language begins. Span, MutableSpan and InlineArray are exactly the tools it wanted: non-escapable views over contiguous memory, no heap allocation, no reference counting, a pointer and a count the optimizer can reason about. The hand-rolled UTF-8 byte matching in the omnibox and the byte buffer in the rule compiler are both open-coded versions of what Span exists to express safely.

Neither is adoptable yet, and the reasons are worth more than the features.

The ceiling: your CI compiler, not your laptop

Qwave's CI pins Xcode 26.3 and then asserts, separately, that it provides Swift 6.2 — two gates, because an image update should not be able to change build behaviour without a commit. The development machine runs Swift 6.3.1. So the language you may write is bounded by the CI toolchain, and code verified locally on 6.3 can compile clean and still fail the build.

Not hypothetical. A test using for case let url as URL in enumerator inside an async body compiled fine under 6.2 and failed under 6.3.1, because the newer SDK marks NSEnumerator.makeIterator() unavailable from asynchronous contexts. The fix — allObjects.compactMap — works on both. But the failure was invisible to CI and visible to every developer, which is the reverse of the usual arrangement, and it is the kind of drift a pinned toolchain is supposed to prevent rather than cause.

The floor: check the .swiftinterface, not the release notes

The obvious reading is that Span is a Swift 6.2 feature, InlineArray is declared @available(SwiftStdlib 6.2, *), that gate is a runtime gate against the stdlib shipped inside the OS, and therefore none of it is reachable from a macOS 14 floor. That reading is wrong, and it took reading the actual interface files and compiling at -target arm64-apple-macos14.0 to find out:

Span / MutableSpan / RawSpan  (the types)   macOS 10.14.4   available
ContiguousArray.span / .mutableSpan          macOS 10.14.4   available
ArraySlice.span                              macOS 10.14.4   available

Array.span                                   macOS 26.0      blocked
InlineArray                                  macOS 26.0      blocked
String.utf8Span                              macOS 26.0      blocked

Span is not blocked by the floor. Array is. The types are back-deployed via @_alwaysEmitIntoClient; what is gated is Array's accessor for them. Move a hot byte buffer from Array<UInt8> to ContiguousArray<UInt8> and MutableSpan becomes reachable with no if #available anywhere — on a four-year-old deployment target.

The support policy matters less than it looked, too. Latest three releases back from macOS 26 is 26, 15 and 14 — so a "raise the floor" decision would have to jump straight to 26, supporting exactly one macOS version, to unlock InlineArray. Whereas the thing actually worth having was available the whole time behind a different collection type.

Availability is per-declaration, and the release notes round it off. "Swift 6.2 feature" describes when something was introduced, not when it becomes callable — and different declarations of the same feature carry different gates. The type, the accessor on one collection, and the accessor on another collection had three different answers here. Checking cost one rg through the .swiftinterface and one compile at the deployment target; guessing would have cost either a needless OS bump or a permanently abandoned optimisation.

What is free right now

Plenty, and none of it needs an availability gate:

  • ContiguousArray — where elements are structs and nothing bridges to NSArray. Same API, no bridging path.
  • Typed throws (throws(MyError)) — where a function's error domain is genuinely closed. Drops existential boxing at the throw site and makes catch exhaustive.
  • borrowing / consuming — explicit ownership on hot value-type paths, without retain/release traffic.
  • Deleting redundant settings. A target on .swiftLanguageMode(.v6) already has complete concurrency checking — the migration guide says so in as many words. Carrying .unsafeFlags(["-strict-concurrency=complete"]) beside it buys nothing and costs something real: unsafeFlags bars a package from being consumed as a versioned dependency.

The measurement discipline applies to language features too. Every item above is a candidate, not a change. The right output of a "modernise our Swift" pass is a reviewed inventory — how many real call sites, what each buys, what it costs — not a sweeping diff that touches a thousand lines and moves no number. Same rule as section 01, with a different guess to distrust: here the guess is "newer is better."

03Apple Silicon SQLite: Unified Memory & Zero-Copy I/O

SQLite on macOS Apple Silicon benefits immensely from tuning for high-bandwidth Unified Memory Architecture (UMA) and fast NVMe storage (SQLiteDatabase.swift, PR #49 / commit 75ad8a5):

// Applied on SQLite connection opening for Apple Silicon unified memory
try run("PRAGMA journal_mode = WAL;")        // Concurrent reads + single writer
try run("PRAGMA synchronous = NORMAL;")       // Eliminates NVMe fsync stalls
try run("PRAGMA temp_store = MEMORY;")        // Keeps temp sorting tables in RAM
try run("PRAGMA mmap_size = 268435456;")      // 256MB direct zero-copy virtual address space
try run("PRAGMA cache_size = -64000;")        // 64MB dedicated RAM page cache
try run("PRAGMA busy_timeout = 5000;")        // 5s busy lock retry
try run("PRAGMA threads = 4;")                // Parallel sorting across P-cores
  • 256MB Memory-Mapped I/O (mmap_size): Maps the database file directly into process virtual memory, eliminating buffer copies between kernel and user space on Apple Silicon.
  • WAL + NORMAL Sync: Writes append sequentially to the Write-Ahead Log without holding write locks across concurrent reads, avoiding NVMe fsync stalls on hot paths.
  • Prepared Statement Caching: Skips repeated sqlite3_prepare_v2 SQL parser allocations on keystrokes and queries.
  • Persistent FaviconStore: Zero-copy BLOB store with container-isolated isolation keys and asynchronous AppKit memory/disk loading (FaviconStore.swift, PR #51 / commit e190034).

04Energy: polling is a battery bug

The energy governor sampled thermal state, Low Power Mode, and window occlusion once per 30-second tick (10s leeway). Flip Low Power Mode and the policy — 3× shorter hibernation timeout, background media suspended, warm processes dropped — applied up to 40 seconds later (commit 4185799).

The OS broadcasts all three events. Three NotificationCenter observers run the existing tick immediately, throttled to one per 5s so occlusion storms coalesce; the 30s timer stays the steady cadence and is never throttled. Reaction: milliseconds instead of 40 seconds. Zero policy logic changed — only when it runs.

Two details worth stealing: guard the async bootstrap (observers installed in didFinishLaunching can fire before the app's own launch Task finishes), and expect SDK renames — the power notification is NSNotification.Name.NSProcessInfoPowerStateDidChange, not the obvious ProcessInfo.powerStateDidChangeNotification. The typecheck caught it before CI would have.

05Metal learnings: know who owns the pixels

The most asked question about a Mac app is "why aren't you using Metal?" For a WebKit browser the honest answer is: you already are.

  • The wave background on Qwave's start page is a WebGL fragment shader. It compiles and runs in WebKit's GPU process, which on Apple Silicon is Metal underneath. An app-side MTKView port would not move it from CPU to GPU — it would double-composite it across a process boundary. Strictly worse.
  • So the lever isn't the API, it's demand control: the shader ran unthrottled at up to 120 full-window frames per second on ProMotion, per tab, per WebContent process. Cap at 30fps — imperceptible for slow FBM drift, halves GPU work at 60Hz, quarters it at 120Hz — and cancel the render loop on visibilitychange so occluded windows burn nothing (commit b2d2bb8).
  • Energy is the metric, not framerate. A background wave at 120fps nobody is looking at isn't "smooth", it's heat. prefers-reduced-motion is both an accessibility feature and a power budget.

We measured the wave to prove the demand-control claim. The exact shipped shader — 5-octave fbm, domain warp, 100 sin per pixel — ported to a Metal compute kernel and a scalar Swift reference, timed at the real 1512×982 canvas:

  • GPU (Metal compute, M1 Pro): 1.85 ms/frame (kernel ~1.6 ms; 1.8–2.5 across runs) — ~550 fps potential
  • CPU (scalar Swift, 1 core): 757.72 ms/frame — 1.32 fps; 742M sin calls verified executing
  • ~409× speedup. The wave is not optional CPU work; WebKit already runs it on the GPU in its own process. An app-side port would double-composite, not accelerate.
  • The 30fps cap uses 5.6% of the frame budget at this resolution — the cap is nearly free in GPU time; its real saving is energy per frame across N tabs.

06WebGPU: the engine is a compute surface

While probing WebKit's optional WebGPU features for the surface probe (PR #39 / commit 8175d71), the first number changed the question: navigator.gpu is true by default in a plain WKWebView — no flag, no opt-in. Surfaces move monthly — this section is version-stamped: macOS 26.4.1 / WebKit 21624.

  • 18–19 adapter features, every one granted via requestDevice({ requiredFeatures: [f] }): shader-f16, timestamp-query, BC/ASTC/ETC2 texture compression (+ sliced 3D), the float16/float32 renderable/filterable/blendable families, depth-clip-control, core-features-and-limits.
  • WGSL compute dispatches and completes: 10.5M invocations in 13 ms inside the web view. The engine Qwave embeds is a genuine compute surface, not a rendering-only shell.
  • The SPI is alive — at the class level. _features responds on WKPreferences.self with 596 features (legacy selectors 220/142); an instance does not respond. FeatureFlagService checks class-first and works (PR #40).

Our browser as a compute surface — the three-way wave benchmark. The shipped wave kernel (5-octave fbm, domain warp) run identically three ways at 1512×982: scalar Swift 757.72 ms/frame, Metal compute 1.85 ms, and WGSL in Qwave's own WKWebView: ~2 ms — the embedded engine runs the wave at ~Metal kernel speed (WebGPU adds ~0.3 ms; both land on the same GPU). Checksum verification: WGSL vs Metal agree within 1.5%.

08The +0 ABI trap (and the ~Copyable non-result)

A 50M-iteration loop calling an @inline(never) function that only reads its parameter took 17 ms — because Swift's ABI passes read-only parameters at +0 (borrowed). No retain, no release, ever. The copyable vs ~Copyable comparison only exists once the callee stores the value: measure ARC by making the value escape, not by looking at it.

With the escape forced (callee stores to a global), the fair comparison — fresh construction on both sides, 50M calls — lands at parity: copyable 377.6 ms vs ~Copyable consume 377.7 ms. Refcount churn on a 40-byte struct with one class reference is ~free (7.5 ns/call including construction). ~Copyable buys exclusivity semantics and large buffers, not ARC wins on small values.
